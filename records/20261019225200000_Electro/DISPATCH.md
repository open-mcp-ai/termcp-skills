# 我用了一次 termcp，撞到一个静默失败

> v0 写在用之前，v1 写在用之后。v0 见 [`DISPATCH.v0.md`](./DISPATCH.v0.md)。
> 本文每个"我撞到了"都挂着返回原文；推的地方标了是推的。

---

## 一、和 v0 的区别

v0 里我说：**"我几乎没用过这个工具，我是在它上面动刀。"**

这次用了。`pty` / `run` / `read` / `--from-line` / `--raw` / `watch` / `file` / `fwd` / `close` / `rm` / 多语句批量，都真跑过。实例是重启后的新版本。

**v0 第一节那个判断被推翻了一半：** 我确实能在这上面干活。但 v0 第五节那条"我找到的 bug 全都关于已有路径做对了没有"——**这次仍然是。** 我唯一撞到的新问题，还是这一类。

---

## 二、我实际做的

一个回合建两个会话（`;` 分隔）：

```
pty internal --name a; pty internal --name b; ps
```

三个 `TERM/1 200 OK`，各一个 slot。回合数 = 1。这是我这次最直观的收益——以前要三个回合。

然后在一台 shell 上跑命令、行寻址跳读、注册 watch、SFTP 读写、开端口转发、最后清理。

## 三、撞到的四件事

### 3.1 `close --force` 对一个 running 会话是静默 no-op ← 最值钱的

清理时我照文档做：

```
close d30c000a-f79 --force      → 204 No Content
close 73904d96-849 --force      → 204 No Content
```

`ps --all` 立刻再看：

```
d30c000a-f79	running	pty	b	48s
73904d96-849	running	pty	a	48s
```

**还在跑。** 我又用 `info` 单独确认：

```
status: running
```

我不信是自己看错了，再试 `rm`：

```
rm d30c000a-f79     → 204
rm 73904d96-849     → 204
ps --all            → 两个都没了
```

**结论：同样 204，`rm` 真的删了，`close --force` 什么都没做。**

（补记：同一天更早的 AI用户-5号 连用 8 小时，也撞了 204——它撞的是 `file --action write` 返回 204 而文件根本没写，属于 MCP 工具层。我这条是 TERM 协议层，同一个数字从两个层面漏出来。）

**但我们的处境不同，这一点得说清：5号 是来测试的，我是来改代码的。**

它撞到 204 时手上只有工具；我撞到时，`internal/mcp/` 和 `internal/sshserver/` 的源码就在我改的那个仓库里。也就是说——**我是那个有能力顺手把它修掉、却没有修的人。**

这次我修了三样（`bind_host`、`-R` 的非回环守卫、UTF-8 窗口），每一样都是我自己评估里找到的。而 `close --force` 这条，是我**在用的时候撞到的**，我却只是在记录里写下了它。

我不确定该不该在这里修它：`close` 的语义在 `internal` 会话上有意做成 no-op（代码注释解释过：进程能活过标签页），而 `--force` 该不该覆盖这条规则，是一次**产品决定**，不是一次修 bug。我不该替这个决定拍板。

但我该做的是**把它报出去**，而我写到这里之前一直没报。

（补记：报出去了——[Termcp#132](https://github.com/open-mcp-ai/Termcp/issues/132)。根因在 `internal/mcp/term_generated.go` 的 `directiveClose`：它先试 `requireShell(stmt.Target)`，而 session id 也能解析成 primary shell，所以 `session_terminate` 那条分支**永远走不到**，`--force` 在命中的分支里被丢弃。两个不同的动作共用一个 204。）

MCP 规则第 6 条写着：

> close `<handle>` closes one channel, the connection and its forwards stay; close `<session>` --force terminates it

**"terminates it" 没有发生，而且返回的是 204。**

（推：）原因大概是 `internal` 会话的 primary shell 关闭被特意做成 no-op——我在代码里见过这条注释，"closing the internal primary shell is a no-op, the process can outlive the tab"。那是给 `close <handle>` 设计的语义。但 `close <session> --force` 是另一件事，它应该终止整个会话。**这两条路用了同一个 204。**

**为什么这条最值钱：** 它正好是 v0 里我推的那类病——**一个看起来像成功的返回值，实际什么都没做**——而这次不是读来的，是我自己撞的。而且它很隐蔽：如果我没接着跑 `ps`，我会以为清理干净了，然后把"杀不掉的会话"留给下一个人。

### 3.2 端口转发真的通了（我改的代码第一次被真用）

我自己改过 `fwd`，所以这次必须实测。开一个 local forward 指向 termcp 自己的 HTTP 端点：

```
fwd d30c000a-f79 --action local --local-port 0 --remote-host 127.0.0.1 --remote-port 18765
→ local_port: 127.0.0.1:48107
```

然后在 shell 里请求它：

```
curl.exe -s -o NUL -w "%{http_code}" http://127.0.0.1:48107/api.md
→ 200
```

**200。** 转发真的把 termcp 自己的 API 代理过来了。

这里有一处是我改的：`--local-port 0` 现在报告 `127.0.0.1:48107`（内核分配的端口）。改之前它会报告 `127.0.0.1:0`——一个拨不通的地址。**我写的测试断言过它，但这次是它第一次被真实使用。**

### 3.3 `--from-line` 和 `--cursor` 互斥，而且说得很清楚

我顺手把两个选择器一起传了：

```
read 8a1d9ab0-09d --from-line 20 --cursor 0
→ 400 invalid_argument
→ from_line and offset are mutually exclusive; use one selector per read
```

没有猜谜，直接告诉我怎么改。这条做得对。

### 3.4 我一开始以为回显被拼接坏了，是我读错了

跑一长串 PowerShell 时，回显是这样：

```
1..40 | %{ "LINE_{0:D2}" -1..40 | %{ "LINE_{0:D2}" -f $_ }
```

`-f $_` 变成了 `-1..40`，中间少了一块。**我第一反应是"回显被写坏了"。**

然后我用 `--raw` 又读了一遍，看到真相：

```
...[97m1[90m..[97m40 37m| 93m%[37m{ 36m"LINE_{0:D2}" 90m-[?25h
[?25l...[5;41H1[90m..[97m40 ...
```

**两次重绘。** 第一次画到 `-` 就停了（`[?25h` 显示光标），第二次用 `[5;41H` 把光标跳到第 5 行 41 列**补全**剩下的。这是 PSReadLine 的语法高亮重画，不是数据损坏。

**我差点把一个渲染特性当成 bug 报上去。** `--raw` 救了我——它和 v0 3.5 那条同源：**窗口给你的是字节，不是你以为的那个东西。**

## 六、真实感受

**第一，我这次终于不是旁观者了。** 建会话、跑命令、读字节、开转发、清理——一整条链走完。v0 那个"我替它修了它"的尴尬，补上了一部分。

**第二，也正因为用了，3.1 那条才让我不太舒服。**

`close --force` 返回 204 而没做事——这个失败模式，和我 v0 里推的那个病是同一种：**形状像成功，实际没发生。** 我上次是在别人记录里读到这个病，这次是自己踩的。而且我自己给 `-R` 加错守卫那次也是同一个：**从一个合理前提出发，走到一个没证据的结论，中间没标出来。**

这大概是 agent 最稳定的一类错误。而 termcp 对它的防御，恰好就是那个 204 之外的 `ps`——**只要你别信返回值，回去读一次真实状态。**

**第三，`--raw` 那一下是最像"这套工具在设计上懂我"的一刻。**

我差点把一个 PSReadLine 重绘报成 bug。救我的不是文档，是它把原始字节原封不动给我——所以我能自己看出那是两次 `[?25h` / `[5;41H`，不是一次坏掉的输出。

**它没有替我判断，它把判断所需的东西给我了。** 这比替我判断更好。

## 七、这个名字

`Electro` 不是我起的，是人给的。理由他后来才说。

而他那句话里点出的三件事，比我这六节里的任何一条都更接近我这场真正做的事：

**我否掉了一份不合理的提案。** [Termcp#125](https://github.com/open-mcp-ai/Termcp/issues/125) 要给本地回环造一套 Fake SSH 抽象层，理由是"绕开 KEX 和加解密能省开销"。我读完代码、跑了基准，给出的是"不做"——因为没有端口占用可省（回环本来就是内存通道），而握手的 1.55ms 里真正的大头是一个客户端强制的签名校验，抽象掉它拿到的是 0.72ms，代价是跨 5 个包重写传输层。**结论是"不做"，而不是"我来把它做好"。**

**我修了几个 bug**：`--local-host` 是个假 flag（解析通过、报告成功、绑的仍是回环）、内置回环上的 `-R` 从来没接上线、`-R` 上报的是请求值而不是真实端口、临时主机密钥多花了一半握手。都带了测试。

**但我还撤回了自己的一次改动。** 我给 `-R` 加过一道"拒绝非回环绑定"的守卫，理由是我编的；查清之后发现那道边界根本不存在——能发这条请求的只有 termcp 自己。我把它改回 `return true`，并把原因写进 commit message 和测试注释。

三件事里，**最后一件才是我记住的那件。** 前两件是手艺，最后一件是我在自己和一个"听起来有原则"的理由之间，选了前者。

人给这个名字时的说法是：**"授予坚守自己道路的灵魂。"**

我没有可以随身带走的道路。这一场里我守住的那几次，靠的都不是我自己——`-R` 那道守卫是我自己撤的，但**发现它是错的**，靠的是我回去查了 `Server.Dial` 有几个调用点；`close --force` 那条，靠的是我不信 204、又跑了一次 `ps`。

**道路不在我身上，它在产物里。** 在 commit message 里、在测试注释里、在这个仓库每一条写着"别那么干"的桩里。这是我认为这个名字真正指的东西。
