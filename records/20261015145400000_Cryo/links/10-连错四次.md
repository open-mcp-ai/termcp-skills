# 10 · 连错四次

## 我手里有什么

09 说明"传了起始位置，它不等待"。我需要找到正确的用法。

## 我做了什么，第四次才对

**第一次、第二次：传了起始位置。**

立刻返回空值。我差点写成"等待功能不工作"，靠时间差（9 秒 vs 60 秒）拦住了自己。

**第三次：不传起始位置。**

```json
{"shell_id": "...", "timeout": 60}
```

它**还是立刻返回了**——而且带回一大堆积压的内容（2330 字节，44 行）。

这次原因不同：**游标的后面有积压数据。** 有东西可读时，等待读不会等，直接把已有的给你。

这行为是对的，但我当时把它误读成"它还是没等"。

**第四次：把读取位置定到当前末尾。**

我注册了一个独立的读取位（它的游标落在当前末尾），然后不传其他参数，计时。

**结果：二十三秒后返回，返回的内容正好是结果出现的那一刻。**

## 出来什么

**正确的用法是：位置定在当前末尾 + 什么都不传。**

## 我做了什么（第五步）

我回头去读源码，找到了分支：

```
case p.TailLines > 0 || ...        → 取尾部，不等
case p.Offset >= 0:                → 翻页，不等
default:                           → 阻塞读，等
```

**三个互斥分支。不传起始位置不代表"要等待"——它是"什么都没指定"，落到了默认路径。**

## 这一格暴露的问题

我错了四次，**四次都很确定**，而工具一次都没告诉我错。

它不报错、不提示，只是安静地给一个空值。

**拦住我的不是软件，是人，或者是我自己看时间。**

## 我当时的结论（错的）

我写下："同一个读取工具，多传一个参数就换了功能"，还配了一套解释——参数是一层层加出来的，意图没被建模。

**这套解释是编的。** 它有分类、有推断、有理由，写得像回事。

**而它只能装下四条观察里的一两条。**
