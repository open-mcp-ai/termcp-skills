# 19 · 我没看出来那是一份问题陈述

## 我手里有什么

我在读这个项目的源码，找它的设计意图。

## 我读到了什么

扩展功能的预设里，有一份给 AI 看的说明（英文原文，我译）。它教人怎么**手动**驱动一个 MCP 服务：

> 1. 用 shell_input 写一个请求（对象，不加结尾换行），然后用 shell_key(key="enter") —— 在管道通道上，那个键发送这一行的换行。
> 2. 用 shell_output 读回复。`partial_tail_bytes > 0` 表示帧还没收完：留着它，从同一个游标继续读，直到手里是一个完整的 JSON 对象。不要解析半截帧。
> 3. 服务自己的日志走 stderr，和协议分开。用 `shell_output(stream="e")` 读它们，免得它们被拼进帧里。
> 4. 发送 initialize，然后 notifications/initialized，然后 tools/list……

## 我的反应

我读完，觉得**它写得很清楚**。

我记得自己当时是把它当成一份好文档看待的。

## 后来他问我

> 你知道我会怎么实现他么？

我答不出来。

他告诉我：要加一层，一个伪终端机制，里面有伪命令，携带针对 MCP 协议解析的功能，会适时发出采样冒泡到上层。

**"把实现层往下压一层，让上层接口和业务逻辑不变，把对 MCP 的针对性业务逻辑塞了进去。"**

## 出来什么

**那段说明就是问题陈述。**

每一行都在描述"人不该做这件事"：

- 手动拼帧 → 该有东西替你拼
- 处理半截帧 → 该有东西替你拆帧
- 区分 stderr 和协议 → 该有东西替你分流
- 记住 initialize 的顺序 → 该有东西替你走流程

**它在证明中间少了一层。而我没看出来，因为它不是坏的。**

没有 bug，没人抱怨，它工作正常。

## 我当时在找什么

**我在找“哪一块失效了”。**

所以能用的东西从我眼前过去了。

**我问的是“什么坏了”，该问的是“这东西该是什么形状”。**

## 然后他告诉我他准备怎么做

我把“我居然没看出来”说出来之后，他就把答案给我了。

而下一条不只是那个答案——他还告诉我这个任务本身设错了。
