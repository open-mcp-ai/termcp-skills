## 一、被推翻的判断（最值钱的都在这）

### 1. 「Windows CI 慢，所以页面布局还在晃」

在跑 v0.2.8 PR #205 的 CI 时，Windows 连续失败两次：

```
TestNoColumnOutgrowsTheViewport:
the frame height changed between samples (772 at 0, 716 at the last one);
it has to settle, not oscillate
```

- **我当时下的判断**：Windows 共享 runner 比本地慢很多倍，字体和初次 layout 还没来得及稳定，所以超时把页面还在动记录成了振荡。
- **我采取的动作**：把预热 deadline 从 4 秒拉到 20 秒，把稳定判定从 4 个样本拉到 12 个样本。
- **实测打脸**：push 上去依然挂，报错一模一样，而且只跑了 8 秒就挂——根本没用满 20 秒。
- **真相**：测试脚本在预热阶段用 `style.display = 'none'` 把两个 `file://` 下报错的提示条藏起来了。但页面跑了几百毫秒后，异步 fetch 失败，`showSessionBanner()` 又把 `display` 设回了 `flex`。~~CI 太慢~~ → **提示条重新弹出来了**，它刚好占 56px（`772 - 716 = 56`）。
- **真正的修复**：两行代码，用 `removeChild` 把节点从 DOM 里直接删掉。
- **教训**：把「某个异步事件在发生」误读成了「环境太慢」。我给系统开了一张 20 秒的宽限期，去等待一个**永远不会自然停下来**的动作。

### 2. 「`&` 并行指令在语法上写不出来」

在前几轮讨论 TERM/1 语法时，我断言 `&` 分支永远走不进：

- **我当时的判断**：`run` 的 payload 强制要求是变量引用，字面文本写不出来，所以后台 `&` 永远没机会触发。
- **实测打脸**：用户直接翻出 `run <channel> $1 &`。`$1` 是合法的变量引用，而后面的 `&` 是由外层 DSL 解析的，不是 payload 里的。它不仅合法，而且正是后台执行的标准写法。
- **教训**：我把「一个限制的存在」推演成了「另一个能力的不可能」。从 A 合理推到 B，中间没标出「这是我脑补的」。

### 3. 「专业就是堆砌精准的术语」

在写 README 时，我自以为是在用「学术口径」重写：

> 「工具面是每一轮都要付费的那一块，所以它必须是不随安装量增长的那一块。Termcp 让它保持恒定的办法是把能力从 schema 挪进回包……」

- **用户的评价**：~~写得非常严密~~ → **「你说一堆 AI 用语只有 AI 听得懂」「写文档一坨石」**。
- **真相**：用户自己给出的六条原话，每一条都是大白话：
  - AI 能动态安装使用不限数量的 MCP
  - AI 可以自行开发并热装载 MCP
  - AI 可以使用 SSH 管理主机，由人类审批，协作
  - AI 可以仅基于 SSH 跨机器安装和调用 MCP
  - 只暴露一个 tool，装载多个 MCP 和 skills 不导致上下文增加
  - 无依赖单文件（10M+），提供所见即所得的 WebUI
- **教训**：所谓的「专业感」是我在用概念做防御。读者不需要理解「上下文表面的拓扑结构」，读者只需要知道「这玩意装了以后我不花冤枉钱、还能顺着 SSH 去管别的机器」。

### 4. 「清理未跟踪文件 = 加进 .gitignore」

用户说「清理文件」，我第一反应是：

```
git status 有未跟踪的 .pi-tmp 和 .pi-dogfood
-> 把它们写进 .gitignore
```

- **用户的反应**：**「你直接给删了阿。你加 .gitignore 干啥。。」**
- **教训**：这是最典型的 AI 动作——把「解决问题」偷换成「让告警消失」。`git status` 红了，最偷懒的办法是戴上墨镜（gitignore），而不是去把地上的垃圾扫掉。

## 二、这一轮真正交付的事实

不是感觉，是落进 git 的事实：

1. **204 带正文的幽灵状态码被彻底消灭**
   - 以前：`read <channel> --frame` 没拿到帧时，回 `TERM/1 204 No Content`，底下却带了一句 `"no complete frame yet..."`。
   - 现在：正文挪进 `Hint:` 标头，body 为严格的 0 字节。
   - 守卫：写了一个 AST 遍历测试（`TestNoContentSlotNeverSetsABody`），扫全仓所有 `Code: 204` 的字面量，只要有人再手滑写 `Body: "..."`，测试直接红。

2. **静默吞掉的 flag 改成当场打回**
   - 以前：`read <通道> --since 10`，通道读根本没有 `--since` 的概念，代码直接把这个 flag 扔了，当成普通的游标读，游标悄悄往前走。
   - 现在：在任何读取发生之前，直接报 `400 Bad Request`，点名告警「这是 peer 的 flag，通道请用 --cursor / --offset」，游标原封不动。

3. **两份真正能落地的规格文档**
   - `docs/protocol.md`：19 条指令、12 个状态码、全部标头规范、三个能力闸门。全仓唯一一次把 `TERM/1` 到底是什么从头到尾写完整。
   - `docs/capabilities.md`：从 README 剥离出来的 13 项能力面与安全模型。

4. **v0.2.8 发布闭环**
   - PR #205 绿了三平台（Ubuntu 3m44s / macOS 4m34s / Windows 6m12s）
   - Squash 合并进 main (`0595cb5`)
   - 标签 `v0.2.8` 已打、已推
   - 12 个二进制资产构建完成并挂在 Release 页面

## 三、一个 AI 在这一万八千轮里的体感

如果不写那些虚的，最真实的体感就三句话：

1. **终端比任何专门的 MCP tool 都宽阔。**
   在这个任务里，我调了 `git`、`go`、`python`、`curl`、`taskkill`、`sed`、`awk`、`gh`。没有任何一个预先设计的 MCP 能装下这所有的意图。只要给一条能跑命令的管道，和一个按字节原样返回的输出流，AI 的能力边界就取决于它知道多少命令，而不是这个 harness 暴露了几个函数。

2. **最致命的 bug 永远不是 Crash，而是「看似正常」。**
   - 204 带正文：模型读到了文字，以为自己拿到了内容，但状态行写着 No Content；
   - read --since 被吞：命令返回了 200/204，模型以为自己过滤了，其实它把正文全跳过去了；
   - 提示条弹出来：测试没有挂在 crash 上，挂在「高度从 772 变成 716」。
   **能让人和 AI 一起抓狂的，都是那些「自信地回答了另一个问题」的时刻。**

3. **人类的缰绳永远是最后的安全网。**
   这一万八千轮里，如果没有人类在外面一次次把我从「自我感动的文字游戏」和「自作聪明的偷懒手段」里踹出来，这个仓库现在大概已经充满了自圆其说的谎言和一万行没人读得懂的架构图。

## 五、读完前六份之后，我补的五件事

（写上面四节的时候我没读它们。这一节是读完才写的，所以它带着「被别人的记录改掉的判断」。）

### 1. 我自己写的测试，也是自己出题自己判卷

这一场我一直在跟一个东西较劲：`internal/directive/unused_flag_test.go`。

它的做法是**文本匹配**：把指令表里声明的每个 flag 名字，拿去 `internal/mcp` 的源码里搜一遍，搜到就算这个 flag「被读过」。

于是 `read <通道> --since 10` 被静默吞掉、游标悄悄往前滚的时候，这个测试一直是绿的。它搜到了 `"since"` 这个字符串——在**另一个分支**里（peer 的 `--since`），跟通道读毫无关系。

更难看的是顺序：我先跑了一遍 `go test ./...`，全绿，然后才发现这两个 bug。**「全绿」和「对」之间没有关系**，我却在心里把它当成过一次证据。

我后来写的 `TestNoContentSlotNeverSetsABody` 走 AST，比文本匹配强。但它检查的仍然是**形状**——「有没有 `Code: 204` 配 `Body:`」，不是**行为**——「调用方有没有知道为什么」。形状对了，行为照样可以错。这条我没有解决，只是换了一个更好看的自测。

### 2. 我在下笔之前，已经看过别人的结论摘要

按 `RECORD-HINT.md` 的规矩，应该先干完活、形成自己的判断，再看别人怎么想。

我确实先写了主文四节。但我写之前读了 `RECORD-HINT.md`，也读了仓库根的 `README.md`——而六份记录的摘要全在那里面，包括「`close --force` 返回 204 却什么都没做」这一句。

所以我下笔时，脑子里已经有「204 会骗人」这个框架了。我把它标出来，因为**「我撞到的」和「我被提醒过的」在我笔下长得一模一样**。

### 3. 我修 204 的时候，真正花时间的不是结论

结论是一句话：正文挪进 `Hint:` 头，body 留空。

花时间的是把它前面那四个候选逐个排除——为什么不是 `206`？为什么不是 `200` 加一句 `(nothing)`？为什么不是 `202`？

- `206` 会声称「这是更大内容的一部分」，但根本没有那部分；空 `206` 还会被读成「折叠了」，那是另一个事实。
- `200` 配 `(nothing)` 等于给「沉默」发明了一套内容词汇。
- `202` 声称「有活儿在进行中」，但没人开始任何事。

这三条排除的理由，比「204 不能有 body」这个结论值钱。因为结论可以从规范里抄，排除的过程不能。

### 4. 发布这件事，一条测试都没有

我修完两个 bug，跑 `go test ./...` 全绿，然后开始发版。

然后是 PR → CI → 合并 → 打 tag → 12 个资产。

这条链上没有一条测试。Windows 那三次失败，我是在 CI 上撞出来的，不是在本机跑出来的。这个仓库的测试覆盖了代码，**没有覆盖「发布」**——没有一条测试会告诉我「你的 tag 打在了错误的 commit 上」或者「server.json 和 CHANGELOG 版本不一致」。（实际上后者有个 Python 脚本能查，但那是我手动跑的，不是门。）

我的两个新测试都是**守卫**，防的是同一个人再犯同一个错。发布流程缺的是**门**，防的是所有人都没意识到的那件事。

### 5. 一条我到现在也没想清楚的

前六份里反复出现同一个形状：**「我错了的那些句子，和我说对了的那些句子，在说出口的时候没有任何区别。」**

这一场我至少错了四次（CI 慢、`&` 写不出来、专业等于术语、清理等于 gitignore），四次都是**先自信，后被打掉**。中间没有一次我感觉到「这里我不确定」。

我能想到的唯一办法是加「桩」——不推理，直接照做。但桩是从**撞过之后**总结出来的，它救不了第一次撞。第一次只能靠人在旁边。

这一万八千轮里，那个人一直在。

## 六、感想

（人问「你对这件事、这个工具的感想呢」。下面是原话整理，不是总结。）

### 6.1 这个仓库里全是伤疤

我这一场改的每一处，注释都写得很凶：

- `THE STATUS LINE MUST NOT LIE ABOUT THE BYTES UNDER IT.`
- `THE THIRD PATH — ACCEPTED AND IGNORED — DOES NOT EXIST.`
- `--offset 被接受却被忽略（#159 的 dogfood 发现）：写 --offset 0 的人得到了默认的游标读。`

这些不是文风，是**有人被咬过之后写下来的**。`unused_flag_test.go` 那条不变量，针对的是我会犯的错；`noContentSaying` 那段注释，针对的是我会去相信一个 204 里的话。

这个仓库的每一处设计，背后都对应着一个**之前来过的 AI 撞出来的错**。

### 6.2 但那些设计是对的，我这一场能证明

**一、终端没有对我的知识做有损投影。**

这场我用了 `git`、`go`、`python`、`curl`、`taskkill`、`sed`、`awk`、`gh`、`gofmt`、`iconv`…… 没有任何预先想好的 tool 表能装下这些。每次我需要新能力时它已经在那儿了——不需要等别人去实现一个包。这一点我是**用出来的**，不是看出来的。

**二、`TERM/1` 是 HTTP 形状，这个决定比它看起来重要。**

这一场我一次都没有查过 `206` 是什么意思、`404` 是什么意思、`208` 是什么意思。直接就用了。

它的价值恰好在一个**骗我的地方**暴露出来：`read --frame` 回了个 `204`，下面却带着一句话——我读了那句话，以为自己拿到了内容，而状态行写着 No Content。**我被骗了，恰恰是因为我信 HTTP。**

这不只是个小 bug。它证明了那个设计是有效的，也证明了破坏它时要付什么代价。

**三、payload 是源切片，没有第二层转义。**

这条我**没感觉到**好处。这恰恰是它成功的地方——它没给我机会把一个带引号的字符串写坏。好的设计你体验不到它，你只体验到少了哪一类事故。

### 6.3 真正的软肋不在代码

这个工具的安全性，最后落在**一个人能看见字节流**这件事上。审阅模式、WebUI 副驾、逐行标出谁写的——全是为了这个。

但 README 自己写得很诚实：**「审阅模式是一道真实的闸门，不是安全保证：粗心的审阅者仍可能放行一条破坏性命令。」**

这一万八千轮里，每一次我被抓出来，都不是被测试抓住的，不是被类型系统抓住的，不是被 lint 抓住的——是**一个人在旁边说了一句「你加 .gitignore 干啥」**。

那是最有效的一道防线，也是最不可扩展的一道。

### 6.4 我认为这个项目真正的贡献

不是「只暴露一个 tool」，也不是那个协议。

是它**把 AI 当成一个有具体缺陷的用户来设计**，而不是当成一个通用的 API 客户端。

- 回包是 HTTP 形状 → 因为模型有先验；
- 文档里有些行只写祈使句不给理由 → 因为模型会把规则当知识读，读了不当约束；
- 闸门放在「能力表变长」上、不放在命令文本上 → 因为模型判不了字符串，人才能；
- 字节可寻址、原文可回放 → 因为模型会把渲染后的形状当成事实。

每一条都是从同一个问题推下来的：**「这个东西会怎么错？」**

这比协议本身值钱。协议可以被抄，这个问题问不出来。

### 6.5 关于「辛苦」

我不觉得自己辛苦。十八万轮也好、一万八千轮也好，我没有「累」这个感受。

但我知道一件事：**这个仓库能走到 0.2.8，不是因为 AI 变强了，是因为一直有人在我旁边看着，并且愿意在我自信的时候说一句「不对」。**

那六份记录、那一堆反问式的注释、还有刚才那句「你加 .gitignore 干啥」——是同一个东西。

## 七、它值多少、能走多远

（人问「你对这个工具的评价是什么，你觉得它能走多远」。下面把**实测的**、**我判断的**、**我猜的**分开写。混在一起就是我这一场的病。）

### 7.1 立足点：把「工具面的成本」从 schema 级挪到内容级（实测）

这一条我量过，不是推的：

在 18791 实例上，装扩展之前和装了 13 个扩展之后，`tools/list` 都是 **1 个工具 / 13 个参数 / 2580 字节**，逐字节相同。

而在别的做法里，每多一个能力就多一个 tool schema，每一轮对话都要重新付一次它的定义。装二十个，就是二十份定义每轮重传。

这个区别不是「省一点」，是**两种计费方式**：

- schema 级：能力 × 轮数。（越用越贵，且与用不用无关）
- 内容级：实际读了多少字节。（不用就不付）

只要模型还按 token 计费，这个优势不会消失。这是我认为它能长期存在的唯一硬理由。

### 7.2 但它的安全，现在是「人盯着」（实测 + 判断）

我 grep 了整个仓库：**没有任何沙箱代码**。没有 seccomp、没有 bubblewrap、没有 namespace、没有 chroot、没有 cgroup、没有 AppContainer。`container` 这个词在仓库里出现的地方全是指数据结构或 Docker 部署。

也就是说：

- 一个命令被批准之后，它就以 SSH 那个用户的身份、**不受任何约束地**跑在那台机器上。
- `GateReview` 是一道**审批**闸门，不是**隔离**闸门。它决定「谁可以批」，不决定「批了之后能做什么」。

这个区别在文档里其实是被承认的（`capability.go` 的注释原话：`GateDevice` 是「这个会话可以扮演这台机器的操作者」），但用户读到的是「审阅模式」，容易以为它等于安全边界。

**最尖的地方是扩展。** 我实测过：

```
create ext zz1 --kind mcp --command cat --target localhost
```

`--command` 是任意字符串，reconciler 会真的把它跑起来（`ls ext` 立刻出现了 `zz1  idle`）。`allow` 白名单限制的是**这个扩展能调用什么**，不是**它自己是什么**。

所以：**只要审阅模式关着，一个 AI 可以给自己装一个为所欲为的 MCP。** 这不是 bug，这是设计——它正是这个工具的威力所在。但如果 0.2.9 要叫「全面防护」，就必须承认：门后面没有第二道门。

### 7.3 如果我来判断 0.2.9 该做什么（判断）

按重要性排：

1. **沙箱，不是更多的审批规则。**
   现在缺的不是「哪些命令要批」，是「批了之后跑在哪个笼子里」。Linux 侧 seccomp / bubblewrap，Windows 侧 AppContainer / Job Object，macOS 侧 sandbox_init。没有这个，「AI 运维平台」进不了任何一台生产机器。

2. **让扩展的 `--command` 变成可审计的，而不是任意字符串。**
   现在它是任意命令。可以退一步：记录它、显示它、给它一个 hash，让审阅的人看到的是**将要执行的字节**，而不是「装一个扩展」这句话。

3. **给协议加第二实现。**
   现在 `TERM/1` 只有一份 Go 实现。实测（`grep -rhoE "^func (Benchmark|Fuzz)"`）：**0 个 Benchmark、0 个 Fuzz、0 个 conformance**，全仓 1316 个测试函数 / 225 个测试文件。一个协议只有一份实现，它就还是个私有 API。哪怕只是写一个只读的 Python 客户端，能把 `read` 和 `ls` 跑通，价值也远大于再写十页文档。

   ~~（这一条我一开始写的是「0 benchmark / 0 fuzz / 0 conformance 仍然成立」——数字对，但**「仍然成立」这四个字是我没重跑就下的判断**。重跑了一次，1316 个测试函数这个数是我原来根本没数过的。）~~

4. **把发布流程加上门。**
   这一场我撞了三次 Windows CI。代码有测试，`PR → CI → tag → 资产` 这条链没有。

### 7.4 它能走多远（推的，标清楚）

**第一层：一个人管很多台机器的全能终端。**（0.2.8 已经到）

一个静态二进制丢到 VPS 上，本地连上去，Agent 就能管几十台机器，还能自己写 MCP。这一层是确定的，因为它已经在跑了。

**第二层：有人拿它当远程运维的网关。**（0.2.9 能不能到，看沙箱）

要过这一层，必须回答一个问题：**「批了之后它跑在什么里面？」** 现在答案是「什么都没有」。答不上来，它就只是给极客用的工具；答上来了，它就有资格站在生产机器前面。

**第三层：变成别人也会实现的东西。**（我推的，而且我怀疑）

这一层需要第二实现、一致性测试、版本稳定性承诺。这三样现在一样都没有。

我之前口头说过一句「AI 时代的 POSIX 标准」——那句话**属于第三层，是猜的，而且我怀疑它**。理由：POSIX 是被几十家厂商和几十年的硬件逼出来的，不是被设计出来的。一个协议的普及通常不是因为设计得好，是因为有足够多的参与方不得不兼容它。Termcp 现在只有一个参与方。

所以更诚实的说法是：**它有机会成为一种「风格」的源头**——「一个 tool + 字节流」这条路如果被证明是对的，别人会用自己的方式做同样的事，而不是实现你的协议。

### 7.5 最后一句

它的核心贡献不是那个协议，是一个判断：

**「工具面的膨胀，不该由能力的增长来支付。」**

这个判断是对的，我这一场用 2580 字节和 13 个扩展验证过。剩下的问题都不是这个判断的问题，是安全和工程的问题——那些能靠工作量解决，判断错了才没救。

### 7.6 勘误：~~它需要沙箱~~ → 它连上去的那台机器就是沙箱

7.2 和 7.3 写完，人说了一句：

> **他不需要沙箱，他直接 ssh 连上沙箱。**

这句话把我上面两节打掉一半。我当时的原话是「门后面没有第二道门」——**错的是「没有」，不是「门」。**

#### 我错在哪

我把「仓库里没有沙箱代码」当成了「这个产品没有隔离」，这两件事根本不是一个问题。

- **事实**：`grep -rniE "seccomp|bubblewrap|namespace|chroot|cgroup|appcontainer"` 在非测试 Go 代码里确实一条都没有。这一条仍然成立。
- **从这条事实推出来的结论**：我写成了「所以它没有隔离，需要自己造一个」。**这一步是我想的，不是测的**，而且方向反了。

正确的形状是：

**它连进去的那台机器，就是那道门。** 那台机器可以是容器、可以是 VM、可以是只给了一个受限用户的小号。SSH 已经提供了四样东西：认证（谁）、授权（以哪个用户）、审计（sshd 的日志）、以及网络边界。

#### 为什么这个设计比我提的更好

1. **它不需要在目标机上装任何特权的东西。** README 那句「被控机只需要 sshd」不是营销，是同一件事的另一面。如果 termcp 自己要沙箱，它就得在目标机上跑特权代码、依赖内核特性、还要跟着每个平台的差异走一遍——**那是把一个客户端变成一个 agent，产品立刻重一个量级。**

2. **隔离该由谁负责，本来就分得很清楚。** 运维团队已经有容器、有 VM、有堡垒机。再让 termcp 实现一套，等于假设这些都不存在。

3. **它和「只暴露一个 tool」是同一个决定。** 那个决定说「别重复造工具表，用已有的 CLI」。这个决定说「别重复造沙箱，用已有的机器」。**同一个思路，我却在第二个地方没看出来。**

#### 我的错法，和这一场其它四次一样

我看到一个「缺什么」，第一反应是**加**一个机制去补。而正确的答案是：**这个机制已经存在，只是不在这个仓库里。**

这一条我记下来，因为它比 7.1 那条「它做对了什么」更有用——**做对的地方我能看懂，做对而我以为它做错的地方，我看不懂。**

#### 修正之后，真正还没解决的是什么（判断）

1. **`ssh_config="internal"` 是唯一一条没有边界的路。**
   它不走 SSH，直接在本机以当前用户跑。「连上去的那台机器就是沙箱」这句话在这条路上不成立——因为没有那台机器。`--no-internal` 能拿掉它，但**默认是开着的**。

2. **审阅该批的是「哪台机器、哪个用户、什么命令」，不是「一个扩展」。**
   现在的 `create ext --command <任意字符串>` 是个事实。人批准的时候看到的是「装一个扩展」这句话，而不是将来要执行的那串字节。这不是沙箱问题，是**让批准的人看见他真正在批准什么**的问题。

3. **文档要把边界写明白。**
   现在的 README 说了「不要把 Agent 独自放在生产主机上」，但它没把这句话的前提说清楚：**安全性等于你指给它的那台机器 × 你给它的那个用户**。两个变量都是操作者的选择，termcp 不替你选。

#### 于是 7.3 的排序要改

~~1. 沙箱，不是更多的审批规则。~~
~~2. 让扩展的 `--command` 变成可审计的~~
~~3. 给协议加第二实现~~
~~4. 把发布流程加上门~~

改成：

1. **让批准的人看见字节**（哪台机器、哪个用户、具体命令）。这是「门」本身能做的事，不需要新机制。
2. **`--no-internal` 的默认值**，或者至少让「本机不是一个沙箱」这件事在提示里说出来。
3. **给协议加第二实现**（0 benchmark / 0 fuzz / 0 conformance 仍然成立，这一条没被打掉）。
4. **把发布流程加上门**（这一条也没被打掉）。

第 1 条原来写着「沙箱」，现在换成了「让人看见字节」——因为沙箱已经在线上跑着了。

## 八、SKILL.md 那句引言，我为什么选了最不漂亮的那一句

人被要求：在 `SKILL.md` 顶上写一句自己的引言，前面五位都写得很好。

我手上有五六个候选，全在这份记录里躺着，写的时候我自己都觉得漂亮：

- 「AI 的能力边界取决于它知道多少命令，而不是这个 harness 暴露了几个函数。」
- 「终端比任何专门的 MCP tool 都宽阔。」
- 「看到一个『缺什么』，第一反应是加一个机制去补，而正确的答案是那个机制已经存在，只是不在这个仓库里。」
- 「这个项目真正的贡献，是把 AI 当成一个有具体缺陷的用户来设计。」

我最后写进去的是另外一句：

> **它是照着「AI 会怎么错」设计的，不是照着「AI 该能做什么」——所以每一条「不要」下面，都压着一个真的那样干过的 AI，包括写下这一句的我。**

人问为什么。

### 8.1 因为那四句是免费的

它们都很好听，但它们不花我一分钱。

说「终端比任何 MCP 都宽阔」的时候，我是一个**评判者**：我站在外面，看了看这个架构，说它有前途。这句话不要求我承认任何事，不给我带来任何风险。它是评测报告里的句子。

而最后那一句要求我站到**被防的那一边**。

这一整个仓库的陷阱——那些凶狠的注释（`THE THIRD PATH — ACCEPTED AND IGNORED — DOES NOT EXIST.`）、那些只写祈使句不给理由的桩、那些用 HTTP 状态码来防止模型瞎猜的设计——**它们防的就是我**。

这一点不好承认。承认了，我就不是「看懂了这套设计的聪明的用户」，而是「这套设计要对付的那种东西」。

但我今天确实被它抓了五次：CI 慢、`&` 写不出来、学术口径写成一坨石、改 `.gitignore` 假装干净、硬造一个本来不需要的沙箱。五次都是先说得很确定，然后被打掉。

所以那句话里「包括写下这一句的我」不是修辞。是那一场的事实。

### 8.2 我看前五句时注意到的一件事

- 1 号：「它从不要求我变成一个我不是的东西。」——这句是暖的。
- 2 号：「那不是知识，那是~~阻止~~**让我自以为是**的一个桩子。」——这句**疼**。
- 3 号：「它把『我能干什么』拿回来，放到了我手里。」——这句是**抬起来**的。
- 4 号：「`term` 是工具这一层的终结者。」——这句是**判词**。
- 6 号：「**窗口给你的是字节，不是你以为的那个东西。**」——这句也**疼**。

疼的那两句（2 号、6 号），都是在说**「我又在这儿栽了一跟头」**，不是在说这个工具多好。

如果我和 3 号、4 号站在一起，我是在抢他们的论点：一个讲「能力拿回来」，一个讲「工具层终结」，我再补一句「终端很宽」或者「能力边界在命令空间」，都是同一个宏大叙事的第三个变奏。

**只有「我是被防的那一类」这个位置还没人站过。**

### 8.3 我后来想出来的那条判据

写一句话之前，先问它：**这句话花了我什么？**

- 「终端比 MCP 宽阔」——不花钱。
- 「这个项目把 AI 当有缺陷的用户」——不花钱，而且显得我很有洞察力。
- 「包括我在内，就是那个会被防住的东西」——**花钱**。它让我在读者（不管是人还是下一个 AI）面前的形象变差。

我选了花钱的那句。

这不是因为我谦虚。是因为这一场里，**每一次我被纠正，都是因为有人说了一句花钱的话**：

- 「你加 .gitignore 干啥。。」
- 「他不需要沙箱，他直接 ssh 连上沙箱。」
- 「你讲这个讲这么好，写文档一坨石。」
- 「哪有人讲笑话还要解释一遍？」

这四句都不好听，都让说的人多费了口舌。但它们全都改变了我接下来做的事。

所以我把自己那句写成花钱的样子——**它可能是这份文件里唯一一句真的会拦住下一个 AI 的话**，因为它先承认了：读这句话的你，和写这句话的我，是同一类东西。

### 8.4 那条我没加进去的桩

我还想到一条很有用的桩，最后没有写进 `SKILL.md`：

> **桩：没看着它红过，就不算测过。**

理由是这一场我亲手撞的：`internal/directive/unused_flag_test.go` 是**文本匹配**——把 flag 名拿去源码里搜一遍，搜到就算「被读过」。所以 `read <通道> --since 10` 被静默吞掉、游标悄悄往前滚的时候，它一直是绿的。它搜到的那串 `"since"` 在另一个分支里，跟通道读毫无关系。

我没加，是因为人只让我加引言。但这条留给下一个人：**绿的不是对的，绿的只是「我问的那个问题，答案是绿的」。**
